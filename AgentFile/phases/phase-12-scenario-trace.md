# Phase 12: 场景追踪（Scenario Trace）

## 定位

本体萃取技能链第 12 阶段，也是最终阶段。通过模拟执行真实业务场景，端到端验证已提取的 Ontology 能否正确支撑实际业务运转。**核心场景追踪无错误是投入使用的前提。**

## 输入参数

| 参数 | 说明 |
|------|------|
| `DOMAIN_CN` / `DOMAIN_EN` | 领域名 |
| `VAULT_PATH` | Vault 路径 |
| `CHAIN_STATE_PATH` | chain-state 文件路径 |
| `INTERVIEW_SUMMARY_PATH` | G2 访谈摘要路径（含场景描述） |
| `OBJECTS_DIR` / `LOGIC_DIR` / `ACTIONS_DIR` / `RULES_DIR` | 各类型目录 |

## 前置条件检查

确认 Phase 11 状态为 `✅ 通过`，否则终止。

## 执行步骤

### Step 1: 收集场景候选

从以下来源整理场景候选清单：

- 访谈摘要中明确描述的"正常流程"和"异常情况"
- G2 确认的核心业务场景
- Logic 文档中的触发条件（每个 Logic 至少对应一个场景）

展示给用户：

```
场景候选清单（共 {S} 个）：

  核心场景（建议全部追踪）：
  【C1】{场景名} — {一句话描述} — 涉及：{Logic/Action 列表}
  【C2】{场景名} — {一句话描述}
  ...

  扩展场景（可选追踪）：
  【E1】{场景名} — {一句话描述}
  ...
```

### Step 2: 用户确认场景范围

> "请确认追踪范围：
>
> - ✅ 全部追踪（{S} 个场景）
> - 🎯 仅核心（{C} 个核心场景，必选）
> - ➕ 补充场景：[描述额外场景]
> - 调整标注：[将 E{n} 升级为核心 / 将 C{n} 降为扩展]"

记录每个场景是否标记为"核心"（core）或"扩展"（extended）。

### Step 3: 更新 chain-state.md 为 in_progress

### Step 4: Dispatch 场景追踪 Agent

读取 `~/.claude/skills/kea/skills/scenario-trace/SKILL.md`，Dispatch：

```
OBJECTS_DIR: {OBJECTS_DIR}
LOGIC_DIR: {LOGIC_DIR}
ACTIONS_DIR: {ACTIONS_DIR}
RULES_DIR: {RULES_DIR}
SCENARIOS: {用户确认的场景清单，含 core/extended 标注}
```

等待完成，获取追踪结果。

**若 KEA 尚无 scenario-trace-agent.md**，改为运行 Python 工具层（对每个场景，找到其主逻辑文件逐一追踪）：

```bash
cd {PROJECT_ROOT} && python3 -m kea --format json trace {LOGIC_DIR}/{场景主逻辑文件名}.md
```

kea trace 接收单个 logic 文件路径，执行其伪代码并输出执行轨迹。若需传入场景数据，使用 `--scenarios {场景JSON文件}` 参数。每个核心场景逐一追踪，汇总结果。

### Step 5: 展示追踪结果仪表盘

```
场景追踪结果：

  核心场景（{C} 个）：
  ✅ 【C1】{场景名} — 执行路径完整，无阻断
  ✅ 【C2】{场景名} — 执行路径完整，规则通过
  ❌ 【C3】{场景名} — 第 3 步执行失败：{原因}
  ⚠️ 【C4】{场景名} — 可通过但有警告：{描述}

  扩展场景（{E} 个）：
  ✅ 【E1】{场景名} — 执行路径完整
  ❌ 【E2】{场景名} — {原因}

  ─────────────────────────────
  核心场景通过率：{CP}/{C} ({CPP}%)
  扩展场景通过率：{EP}/{E} ({EPP}%)
```

### Step 6: 处理失败场景

对每个追踪失败的场景（❌），展示详情并询问处置方式：

```
[场景追踪失败] 《{场景名}》

  失败位置：{Logic/Action 名称} → 第 {N} 步
  失败原因：{具体描述}
  
  受影响文件：
  - {文件路径1}
  - {文件路径2}

  处置方式：
  A 修复文档：[说明修复内容]
  B 修复场景描述：该场景描述有误，实际业务不存在此路径
  C 标注为已知缺陷：[填写原因和计划修复时间]
```

记录每个失败场景的处置方式和修复记录。

### Step 7: 回归追踪

如选择 A（修复文档），修复后对受影响场景**重新追踪**，确认修复有效。

如修复引入新的失败，重复 Step 6-7，直到核心场景全部通过或标注为 C（已知缺陷并承认风险）。

### Step 8: 保存追踪报告

报告保存至：
```
{VAULT_PATH}/RAWData/KEAOutput/reports/validation/{YYYY-MM-DD}-{DOMAIN_EN}-scenario-trace.md
```

## 门控评估（G12）

### 自动验证项

| 条件 | 通过标准 | 是否可绕过 |
|------|---------|---------|
| ① 核心场景追踪无未处置失败 | 所有 core 场景：✅ 通过、⚠️ 已接受（原因非空），或 C 标注（已知缺陷，原因非空） | **❌ 不可绕过** |
| ② 失败场景有处置记录 | 每个 ❌ 场景均有 A/B/C 处置方式且描述非空 | ❌ 不可绕过 |
| ③ 追踪报告已保存 | 报告文件存在 | ❌ 不可绕过 |

**核心场景零未处置失败**是硬性条件：核心场景不能有既未修复、也未明确标注为已知缺陷的 ❌ 状态。

扩展场景失败不阻断通过，但必须有处置记录。

### 人类确认

条件全部满足后询问：

> "场景追踪完成：
>
> - 核心场景 {C} 个：✅ {CP} 通过 / ⚠️ {CW} 警告已接受 / 🔖 {CD} 已知缺陷
> - 扩展场景 {E} 个：✅ {EP} 通过 / ❌ {EF} 失败已记录
>
> **本体提取完整流程已结束。请确认本体可以投入使用：**
>
> - ✅ 确认：本体可以投入使用
> - ✏️ 还需调整 [说明]"

**此确认代表人类专家对整套 Ontology 的最终背书。**

## 门控失败 → 回退处理

**核心场景追踪失败，修复文档后仍失败**：

| 失败类型 | 回退目标 | 处置方式 |
|---------|---------|---------|
| 对象属性缺失导致执行阻断 | Phase 5（对象，增量） | 补充缺失属性 |
| 逻辑分支缺失 / 流程不完整 | Phase 6（逻辑，增量） | 补充分支或修正流程 |
| 动作参数不匹配 / 动作缺失 | Phase 7（动作，增量） | 修复或补充动作 |
| 规则条件导致场景阻断 | Phase 8（规则，当前） | 修正规则条件 |
| 补充提取后重新发现语义/结构问题 | Phase 9 → 10 → 11 → 12 | 走快速通道 |

回退后从修复的 Phase 开始，依次经过后续校验阶段（快速通道：若补充文档子集通过 rule-check + semantic-check，可直接重跑 Phase 11→12）。

在 chain-state.md 追加回退记录。
