# Phase 4: 流程图校验（Flowchart Validation）

## 定位

本体萃取技能链第 4 阶段。对 Phase 3 生成的 Mermaid 流程图执行**结构校验**和**语义逻辑校验**，发现逻辑漏洞并通过人类确认修复，确保流程图作为提取基准的正确性。

**核心准则**：
- 发现问题**只报告，用户授权后才修复**
- 每个语义问题必须有处置记录（修复 / 标注已知问题）
- 严重问题（断路、死路、子流程引用不存在）**不可绕过**

## 输入参数

| 参数 | 说明 |
|------|------|
| `DOMAIN_CN` / `DOMAIN_EN` | 领域名 |
| `VAULT_PATH` | Vault 路径 |
| `CHAIN_STATE_PATH` | chain-state 文件路径 |

目录变量：
```
DIAGRAMS_DIR:          {VAULT_PATH}/30-Ontology/diagrams/{DOMAIN_EN}/
VALIDATION_REPORT_DIR: {VAULT_PATH}/RAWData/KEAOutput/reports/validation/
```

## 前置条件检查

读取 `CHAIN_STATE_PATH`，确认 Phase 3 状态为 `✅ 通过`，否则终止。

## 执行步骤

---

## Phase A — 结构校验

### Step A1: 运行结构分析

```bash
cd {PROJECT_ROOT} && python3 -m kea mermaid {DIAGRAMS_DIR} --format json
```

读取输出，提取每个流程图的以下信息：
- 节点列表（类型、标签）
- 边列表（源、目标、标签）
- `decision_branches()` 结果（判断节点 → 出路边映射）

### Step A2: 结构问题检查

对每个流程图，检查以下 4 项结构规则：

| # | 检查项 | 通过标准 |
|---|--------|---------|
| S1 | 开始节点 | 有且仅有 1 个 START 类型节点 |
| S2 | 结束节点 | 至少有 1 个 END 类型节点 |
| S3 | 判断节点分支 | 每个 DECISION / SUB_DECISION 节点出路数 ≥ 2 |
| S4 | 无孤立节点 | 所有节点（除 START）均有入路，所有节点（除 END）均有出路 |

**如果存在结构错误**，展示：

```
[结构校验] 发现 {N} 个结构问题：

  {流程名1}:
    ❌ [S3] 判断节点 "{节点标签}" 只有 {n} 条出路（需要 ≥ 2）
    ❌ [S4] 节点 "{节点标签}" 无出路（死节点）

  {流程名2}:
    ❌ [S1] 缺少开始节点
```

提示用户修复后，询问：
> "请修复上述结构问题后回复"继续"重新校验，或回复"跳过"直接进入语义校验（不建议）。"

等待用户回复，再次运行 Step A1-A2，循环直到结构全部通过或用户选择跳过。

**如果无结构错误**：告知用户"结构校验通过"，直接进入 Phase B。

---

## Phase B — 语义逻辑校验

### Step B1: 准备流程图数据

为 Dispatch 准备上下文：

1. 对每个流程图，运行 `python3 -m kea mermaid {文件} --format json` 获取解析结果（节点列表、边列表、decision_branches）
2. 收集所有流程图名称，建立**名称清单**
3. 读取每个流程图的 Mermaid 源码

### Step B2: Dispatch 语义校验 Agent

读取 `~/.claude/skills/kea/skills/flowchart-validate/SKILL.md`，Dispatch：

```
MODE: full
FLOWCHART_NAMES: [{名称清单}]
FLOWCHART_DATA:
  - name: {流程名1}
    mermaid_source: |
      {Mermaid 源码}
    nodes: [{id, type, label}, ...]
    edges: [{from, to, label}, ...]
    decision_branches: {node_id: [{to, label}, ...], ...}
  - name: {流程名2}
    ...
```

等待完成，获取 JSON 格式的问题清单。

**若 sub-skill 返回 BLOCKED 或 NEEDS_CONTEXT**：根据原因补充信息后重新 Dispatch。

### Step B3: 生成语义分析报告

解析 sub-skill 返回的 JSON 问题清单，统计各严重等级数量。

报告保存至：
```
{VALIDATION_REPORT_DIR}{YYYY-MM-DD}-{DOMAIN_EN}-flowchart-validate.md
```

报告格式：

```markdown
# 流程图语义分析报告

日期：{YYYY-MM-DD HH:MM}
领域：{DOMAIN_CN}（{DOMAIN_EN}）
分析目录：diagrams/{DOMAIN_EN}/

## 概览

| 状态 | 数量 |
|------|------|
| 有严重问题 | N |
| 有警告 | N |
| 仅建议 | N |
| 无问题 | N |

## 问题详情

> 问题编号全局唯一。回复"修复 1,3"、"全部修复"或"不修复"。

### {流程图名称}

- [#1] **[严重] {问题类型}**
  {具体描述}
  修复操作：{具体说明}

## 无问题的流程图

- **{名称}**：{一句话描述}
```

### Step B4: 展示问题并询问修复意向

向用户展示严重和警告级别问题摘要，询问：

> "语义分析发现 **{X}** 个严重问题、**{Y}** 个警告和 **{Z}** 个建议。
>
> 报告已保存到 `reports/validation/{filename}`。
>
> - 回复 **全部修复** → 自动修复所有问题
> - 回复 **修复 1,3,5** → 仅修复指定编号
> - 回复 **不修复** → 全部标注为待人工处理"

**等待用户回复，不自动继续。**

**若无任何语义问题**：告知"语义校验全部通过"，直接进入门控评估。

### Step B5: 执行授权修复

仅在用户授权后执行：

1. 逐一修复授权的问题，修改对应 `.md` Mermaid 文件
2. 修复后重新运行 `python3 -m kea mermaid {修复的文件}` 确认无新结构问题
3. 对修复的流程图重新 Dispatch `flowchart-validate` sub-skill（`MODE: incremental`，仅检查修改过的流程图）
4. 展示修复结果，若存在新问题循环 Step B4-B5

对于**严重问题**未被修复的情况，记录处置意向：

> "以下严重问题未修复，请选择处置方式：
>
> [#N] {问题描述}
> A 暂时标注为已知问题，继续后续阶段（后续提取时注意此缺陷）
> B 标注为业务真实情况，无需修复"

每个严重问题必须有处置记录才能通过门控。

---

## 门控评估（G4）

### 自动验证项

| 条件 | 通过标准 | 是否可绕过 |
|------|---------|---------|
| ① 语义分析报告已保存 | 报告文件存在且非空 | ❌ 不可绕过 |
| ② 严重问题已处置 | 每个严重问题：已修复 ✅ 或有标注记录 🔖 | ❌ 不可绕过 |
| ③ 子流程引用可解析 | 检查项 10 无未处置的严重问题 | ❌ 不可绕过 |

警告和建议级别问题不阻断通过，但必须在报告中有记录。

### 人类确认

条件全部满足后询问：

> "流程图校验完成：
>
> - 严重问题：{X} 个（✅ {R} 已修复 / 🔖 {K} 已标注）
> - 警告：{Y} 个（已记录）
> - 建议：{Z} 个（已记录）
>
> **这些流程图将作为后续对象/逻辑/动作提取的业务基准。请确认：**
>
> - ✅ 确认：流程图可作为提取基准
> - ✏️ 还需调整：[说明]"

> "G4 通过。**下一阶段：对象提取（Phase 5）**
> 是否现在继续？[继续 / 暂停]"

## 门控失败 → 回退处理

| 失败类型 | 处置 |
|---------|------|
| 严重问题无处置记录 | 必须对每个严重问题选择 A 或 B 处置 |
| 修复后引入新结构问题 | 修复新问题，重新执行结构校验 |
| 用户认为需要重新生成流程图 | 回退至 Phase 3，重新生成指定流程图 |

在 chain-state.md 追加回退记录。
