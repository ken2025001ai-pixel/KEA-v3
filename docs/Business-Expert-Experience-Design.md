# KEA 业务专家体验设计

> **Version**: 1.0  
> **Date**: 2026-04-24  
> **Target User**: 业务专家（非技术人员）  
> **Design Goal**: 让业务专家通过自然对话，将业务知识和经验沉淀为结构化 Ontology

---

## 1. 用户画像与核心痛点

### 1.1 用户画像

| 属性 | 描述 |
|------|------|
| 角色 | 业务经理、领域专家、产品经理、流程Owner |
| 技术能力 | 熟悉 Word/Excel，可能使用 Obsidian 做笔记，不懂编程 |
| 业务深度 | 对所在领域有 5-15 年经验，脑子里有完整的业务图景 |
| 时间压力 | 本职工作繁忙，只能用碎片化时间参与 |
| 表达习惯 | 习惯用业务语言描述，不擅长结构化文档写作 |
| 对 Ontology 的认知 | 可能没听过这个词，但理解"把业务规则整理清楚"的价值 |

### 1.2 核心痛点

```
业务专家的日常困境:

"我知道采购流程是怎么跑的，但让我写成文档..."
  ├── 不知道从哪里开始写
  ├── 写了 20 页 Word，开发说"看不懂"
  ├── 换了新系统，之前的文档没人更新，过时了
  ├── 新人来了，我只能口头教，同样的内容重复 10 遍
  └── 评审会上，开发和业务对同一个词理解不一样
```

**KEA 要解决的不是"自动化"，而是"让业务专家愿意表达、能够表达、表达得准"**。

## 2. 设计原则

### 2.1 以对话代替命令

| ❌ 不要 | ✅ 要 |
|--------|------|
| "请运行 `/ontology-extract`" | "让我们从您最熟悉的流程开始，您负责哪个业务环节？" |
| "填写 YAML front matter" | "这个对象还有哪些常用的叫法？我帮您记下来" |
| "Phase 1/2/3 提取" | "我们先理清楚有哪些关键角色和数据，再聊他们怎么配合" |

### 2.2 先确认再生成

| ❌ 不要 | ✅ 要 |
|--------|------|
| 生成 20 个文档，然后让用户检查 | 生成 1 个对象，确认正确再继续 |
| 一次性输出完整流程图 | 先生成草图，问"这个顺序对吗？" |
| 直接保存到文件系统 | 先展示草稿，用户点头再保存 |

### 2.3 可视化即反馈

业务专家是**视觉型学习者**——他们需要通过看图表来确认理解是否正确。

- 聊到流程 → 实时生成 Mermaid 流程图
- 聊到对象关系 → 实时生成对象关系图
- 聊到影响范围 → 实时高亮关联文档

### 2.4 容错与回溯

| 场景 | 设计响应 |
|------|---------|
| 专家说"不对，审批不是 2 个人，是 3 个人" | Agent: "明白了，我把审批节点改为'部门经理→财务总监→总经理'，对吗？" |
| 专家说"等等，我漏了一个状态" | Agent: "好的，在'已发货'和'已入库'之间补充'运输中'状态，还有其他遗漏吗？" |
| 专家说"这个逻辑太复杂了，我先说个简单的" | Agent: "没问题，我们先聚焦在标准流程，异常处理可以稍后补充" |

## 3. 用户旅程地图

### 阶段 0: 发现与动机（Obsidian 外部）

```
业务专家在什么情况下会使用 KEA？

触发事件:
  ├── 公司要上新的 ERP/业务系统
  ├── 部门要梳理 SOP（标准操作流程）
  ├── 准备给新人做培训材料
  ├── 要和开发团队对齐需求
  └── 领导要求"把业务流程文档化"

专家的心理:
  "我不想写文档...但如果有个工具能帮我把脑子里的东西整理出来，我愿意试试"
```

### 阶段 1: 首次接触（Onboarding）

**目标**: 让业务专家在 5 分钟内理解 KEA 能帮他做什么，建立信心。

```
专家打开 Obsidian，看到 KEA Skill 的欢迎消息:

"欢迎使用 KEA — 业务知识沉淀助手 🎯

我是您的业务知识整理助手。我的工作是:
  ✓ 听您描述业务流程
  ✓ 帮您整理成清晰的结构图
  ✓ 生成团队都能看懂的文档

您不需要写代码，不需要记格式。
只需要像跟我聊天一样，描述您的工作。

【开始】→ 我们从您最熟悉的业务环节开始
【看示例】→ 先看一个已完成的采购流程示例
"
```

**关键设计**: 
- 零配置启动，不需要安装插件（推荐插件可以后续提示）
- 提供【看示例】降低心理门槛
- 不展示任何技术术语（Mermaid、YAML、Ontology 等）

### 阶段 2: 知识访谈（核心交互）

**目标**: 通过结构化对话，逐步提取业务知识。

#### 2.1 开场：确定领域

```
Agent: "您好！为了更好地帮您整理，我想先了解几个背景问题:

1. 您负责的是哪个业务领域？
   比如：采购、销售、库存、财务..."

[专家]: "我是采购部的，负责供应商管理和采购执行"

Agent: "明白了！采购部。那我先确认一下，采购部最核心的
   几个'东西'（数据/单据）有哪些？
   
   不用想太全，先列您每天打交道的："

[专家]: "采购申请、采购订单、供应商档案、入库单..."

Agent: "好的，我记下了 4 个。我们先聚焦在【采购订单】上，
   因为这个听起来是核心单据。您看可以吗？
   
   或者您想先从哪个开始？"
```

**设计要点**:
- 用"东西"代替"对象"，用"单据"代替"文档"
- 每次只聚焦一个主题，不贪多
- 给专家选择权（"您看可以吗？"）

#### 2.2 深入：对象属性

```
Agent: "好的，我们来看【采购订单】。

一张采购订单，上面通常有哪些信息？
比如：订单号、供应商名称、金额..."

[专家]: "订单号、供应商、采购员、金额、交货日期、
   物料明细（品名、数量、单价）、状态"

Agent: "我整理了一下，您看对吗？

┌─────────────────────────────┐
│ 采购订单                      │
├─────────────────────────────┤
│ • 订单号（唯一编号）          │
│ • 供应商（哪家供货）          │
│ • 采购员（谁下的单）          │
│ • 总金额                     │
│ • 交货日期                   │
│ • 状态（现在走到哪一步了）    │
│ • 物料明细（多个商品）        │
│   - 品名、数量、单价          │
└─────────────────────────────┘

'状态'有哪些可能的值？
比如：草稿、已提交、已审批..."

[专家]: "草稿、审批中、已批准、已下单、已发货、已入库、已关闭"

Agent: "好的，7 个状态。我注意到从'已批准'到'已关闭'
   中间有好几步，这些状态变化有什么规则吗？
   比如什么情况下会'关闭'？"
```

**设计要点**:
- 用可视化卡片展示对象属性，降低认知负担
- 追问状态流转规则（为后续 Logic 提取做准备）
- 适时连接相关概念（"从已批准到已关闭中间有好几步"）

#### 2.3 流程梳理

```
Agent: "现在我们对采购订单有了基本了解。

您能描述一下，一张采购订单从'草稿'到'已关闭'
的完整旅程吗？不用太详细，先讲主流程。

就像讲故事一样：
'采购员先做什么，然后谁审批，然后...'"

[专家]: "采购员在系统里创建申请，填好物料和供应商，
   提交给部门经理。经理如果同意就批准，
   如果金额超过 10 万还要财务总监批。
   批准后生成正式订单发给供应商。
   供应商发货，仓库收货入库，财务付款。"

Agent: "我画了一个流程草图，您看看对不对：

[展示 Mermaid 流程图]

我注意到几个点想确认：
1. '金额超过 10 万'这个判断，还有其他判断条件吗？
   比如特定物料、新供应商？
2. 如果经理不批准，订单去哪里？直接关闭还是退回修改？
3. 仓库收货时如果数量不对，怎么处理？"
```

**设计要点**:
- 用"讲故事"降低结构化表达的压力
- 生成草图后立即确认
- 主动追问异常分支（业务专家容易忽略异常路径）

#### 2.4 异常与边界

```
Agent: "您刚才提到仓库收货数量不对的情况。

您能想到哪些'数量不对'的具体场景？
比如：少发了、多发了、发错了..."

[专家]: "主要是少发和质量问题。少发的话按实际入库，
   差额部分让供应商补发。质量问题就拒收，
   通知供应商换货。"

Agent: "好的，我补充到流程图里：

[更新后的 Mermaid 流程图，高亮异常分支]

还有其他异常情况吗？比如：
- 供应商迟迟不发货？
- 订单下了但客户取消？
- 价格变动？"
```

**设计要点**:
- 异常场景需要 Agent **主动启发**（专家往往默认"大家都知道"）
- 每次补充后更新可视化，让专家看到变化
- 逐步穷尽，不追求一次到位

### 阶段 3: 确认与保存

```
Agent: "好的，经过刚才的对话，我整理了以下内容：

【对象】
  ✓ 采购订单（7 个属性，7 个状态）
  ✓ 供应商（5 个属性）
  ✓ 采购申请（4 个属性）

【流程】
  ✓ 创建采购订单（标准流程 + 3 个异常分支）
  ✓ 审批采购订单（2 层审批规则）

【动作】
  ✓ 提交申请
  ✓ 审批订单
  ✓ 通知供应商

这些内容我保存到您的知识库中，
生成结构化的 Ontology 文档和关系图。

您可以在 Obsidian 中随时查看和修改。

【保存并生成索引】 【再补充一些内容】 【先不保存】"
```

### 阶段 4: 持续迭代

```
几天后...

Agent: "上次我们整理了采购流程。

最近有想到需要补充的内容吗？
比如：
- 新的审批规则？
- 新的单据类型？
- 流程变化？"

或者您可以随时说：
- "帮我看看采购订单的逻辑" → 展示现有内容
- "修改审批规则" → 进入编辑模式
- "生成培训文档" → 基于 Ontology 生成人类可读文档
```

### 4.2 Agent 角色切换

在同一个对话中，Agent 需要切换不同角色：

| 场景 | Agent 角色 | 行为 |
|------|-----------|------|
| 开场 | 引导者 | 问候、降低门槛、提供选择 |
| 聊对象 | 记录员 | 听、整理、确认、可视化卡片 |
| 聊流程 | 画图师 | 实时生成流程图、追问分支 |
| 聊异常 | 挑战者 | "如果...怎么办？"启发边界场景 |
| 确认时 | 校对员 | 汇总展示、高亮关键信息 |
| 修改时 | 编辑助手 | 精准定位、建议替代方案 |

## 6. 关键设计决策

### 决策 1: 是否隐藏技术概念？

**选择**: **隐藏**，但不过度隐藏。

| 概念 | 对用户展示为 | 何时暴露 |
|------|------------|---------|
| Ontology | "业务知识库" | 用户主动询问时 |
| Object | "单据/数据/关键概念" | 不需要暴露 |
| Logic | "流程/规则" | 不需要暴露 |
| Action | "操作/动作" | 不需要暴露 |
| Mermaid | "流程图" | 用户想编辑时提及 |
| YAML FM | 完全不展示 | 技术文档中说明 |
| relations | "关联关系" | 关系图审查时 |

### 决策 2: 是否强制流程图？

**选择**: **推荐但不强制**。

- 对于复杂流程：先生成草图，专家确认后再提取
- 对于简单流程：直接对话提取，跳过可视化
- 对于已有文档：从文档直接提取

### 决策 3: 保存时机？

**选择**: **专家确认后再保存**。

- 对话中只生成"草稿"
- 专家说"对的"才写入文件系统
- 支持"先保存草稿，后续再完善"

### 决策 4: 是否支持多人协作？

**选择**: **V1 不支持，设计时预留**。

- V1 聚焦单人对话式提取
- 预留 domain 字段用于后续多人分领域协作
- 预留 status 字段用于审核工作流

## 7. 成功指标

| 指标 | 目标 | 衡量方式 |
|------|------|---------|
| 首次完成时间 | < 30 分钟 | 从开场到保存第一个对象+逻辑 |
| 专家满意度 | > 4/5 | 事后问卷："这个过程比我写 Word 轻松吗？" |
| 知识完整度 | > 80% | 与专家事后补充的内容对比 |
| 返工率 | < 20% | 保存后 7 天内重大修改的比例 |
| 持续使用率 | > 50% | 首次使用后 30 天内再次使用的比例 |

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Agent 理解偏差 | 高 | 每个关键点都确认，可视化反馈 |
| 专家时间碎片化 | 中 | 支持随时暂停/恢复，保存中间状态 |
| 专家不知道要说什么 | 中 | Agent 主动启发，提供示例和选项 |
| 生成的文档技术化 | 中 | 技术细节由底层处理，只展示业务内容 |
| 多轮对话后上下文丢失 | 高 | 显式维护对话摘要，定期汇总已确认内容 |
